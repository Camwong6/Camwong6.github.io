Overview

Twitch Analytics is an end-to-end data platform that collects, stores, and visualizes live Twitch viewership. Every six hours an automated pipeline pulls the top games and their most-watched channels straight from the Twitch API, writes each run as an immutable snapshot into a Postgres database, and serves the accumulated history through a Next.js dashboard with KPI cards, top-10 tables, and trend charts. A natural-language assistant sits on top of the stored metrics so the data can be queried in plain English. I built it because most portfolio projects start from a pre-cleaned CSV, and I wanted to own the whole workflow: sourcing the data, making it trustworthy, modeling it, and explaining what it says.

Architecture

The system is a full-stack pipeline with a clear separation between ingestion, storage, and presentation:

  • Ingestion (Python): OAuth2 authentication against the Twitch API, paginated stream collection (with a safety cap), and a database adapter that writes each run in a single transaction.
  • Storage (Supabase / Postgres): a normalized four-table schema with row-level security enabled deny-by-default, plus indexes powering the trend and top-N queries.
  • API + UI (Next.js on Vercel): a read endpoint (GET /api/metrics) returning the latest snapshot plus history, a protected refresh endpoint (POST /api/refresh), and a Recharts dashboard.
  • Scheduling (GitHub Actions): a cron workflow runs ingestion every six hours and auto-deploys on push to main.

Data Model

Every run is stored as an immutable time-series snapshot, so history is never overwritten:

  • games: the tracked category catalog (top 10 refreshed daily; untracked games retain their history).
  • ingestion_runs: one row per collection run, timestamped and used as the snapshot key.
  • game_metrics: viewers and live-stream counts per game per run.
  • top_streams: the top channels captured in each run, with viewer counts, titles, and verified status.

A few integrity decisions mattered here. The run timestamp acts as a unique key, so re-running ingestion never double-counts. Each snapshot is written in one transaction, so the database never holds a half-loaded run. An is_estimate flag marks any category whose collection was truncated by the pagination cap. I also sized column types against actual value ranges (peak viewership sits in the low tens of thousands, well inside an int) and left the small games table denormalized on purpose.

Insights

I mined the accumulated snapshots for concrete findings. The window below covers 12 snapshots over roughly 38 hours (2026-07-06 to 2026-07-08), so treat these as directional signals; the pipeline keeps accumulating history, and the numbers sharpen over time.

Finding Detail
Viewership is winner-take-most In the most recent full snapshot (~790k viewers across 10 games), Just Chatting alone accounts for 30% of tracked viewers and the top 3 categories account for 54%. Everything below that is a long tail.
Viewers-per-stream splits categories into two shapes Dividing viewers by live streams shows whether a category is star-driven or community-driven. IRL runs ~245 viewers/stream (a few large broadcasters carry it) while Fortnite (~13) and Dead by Daylight (~11) ride a massive long tail of small streams, a ~20× spread that raw viewer totals would never surface.
Prime-time swing is ~2× On a like-for-like basis, total viewership peaks around 22:00 UTC (EU evening / US afternoon) and bottoms around 09:34 UTC (Americas overnight), a 213% peak-to-trough swing within a day.
Independent runs agree When a scheduled run and a manual refresh land a few minutes apart, the two independent measurements of the same moment agree within ~0.1–3% (e.g. 206,319 vs 206,566 viewers), which doubles as a free reliability check on the ingestion.

Data-Quality Note

A naive read of the raw history shows a "551% intraday swing" peaking at 790k viewers. That number is an artifact. The most recent snapshot tracks 10 games; every earlier snapshot tracks only 5 (the fixed list in use before the dynamic top-10 feature deployed mid-window). Summing all games per run therefore compares 5 categories against 10. To correct for it, I restricted every cross-run comparison to the 5 games present in all 12 runs (Fortnite, Marvel Rivals, Minecraft, Overwatch, VALORANT); on that apples-to-apples basis the real intraday swing is 213%. Totals from the single most-recent 10-game snapshot are internally consistent and valid on their own. One more omission worth explaining: verified streamers show ~1.6× the median viewers of unverified ones in the latest snapshot, but only 5 of the top 100 streams are unverified, so the sample is too small to report.

Dashboard & AI Assistant

The front end presents KPI cards with snapshot-over-snapshot deltas, a top-10 categories table, sortable top-channels tables with verified checkmarks and estimate badges, and Recharts trend lines over a 24-hour window with 6-hour ticks. A conversational "Ask the data" assistant answers natural-language questions over the stored metrics (e.g. "which game grew the most today?") and can drive whitelisted visualization commands such as hiding or showing series, toggling log scale, and resetting the view. The assistant is provider-agnostic (Gemini by default, switchable to Claude or OpenAI) and sits behind a per-IP rate limit of 8 requests per minute.

Engineering Practices

  • CI/CD & scheduling: GitHub Actions runs ingestion every six hours and auto-deploys the dashboard on push to main.
  • Security: secrets live in environment variables (never in code or the frontend), the database enforces deny-by-default row-level security, the manual-refresh endpoint requires a secret, and the AI endpoint is rate-limited.
  • Testing: the ingestion layer is covered by a passing test suite with checks that no secrets leak into logs.
  • Idempotency: snapshot-keyed writes make every run safely repeatable.

Limitations

  • The API exposes public viewership data only; monetization metrics (ad revenue, subscriptions) are visible only to the broadcaster and cannot be collected.
  • Insights are drawn from a short (~38-hour) window, so they describe days, not seasons.
  • Two snapshots taken within the same second would collide on the timestamp key. This is a documented edge case that hasn't come up under normal 6-hour scheduling.

Conclusion

Twitch Analytics covers the full analyst pipeline from raw API to communicated insight. The engineering (automated ingestion, a snapshot-based schema, CI/CD scheduling, cloud deployment) exists to serve the analysis: viewership is winner-take-most, viewers-per-stream separates star-driven from community-driven categories, and prime-time viewership roughly doubles across a day. The part I'm proudest of is catching the 551% "trend," tracing it to a mid-window schema change, and correcting it before it made it into any finding.
